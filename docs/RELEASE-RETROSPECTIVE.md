# 发布复盘

本文记录发布过程中实际发生的问题和可执行的防复发规则。发布操作前应同时阅读本文件与 [分支与发布流程](RELEASING.md)。

## 1.1.6（2026-08-14）

### 结果

1.1.6 最终从受保护的 `main` 合并提交创建标签，Release 工作流、安装包验证和 SHA-256 校验均成功。期间产生的错误标签没有形成正式 Release，随后已删除并在正确提交上重新创建。

### 发生的问题

1. 发布修改先提交在本地 `main`，没有先创建短期发布分支。
2. 推送前没有确认 `main` 的保护规则，直接推送被 GitHub 拒绝。
3. 推送 `main` 和推送标签写在同一条 PowerShell 命令中。前一步原生命令失败后 PowerShell 仍继续执行，导致标签过早推送。
4. 错误标签指向尚未进入 `origin/main` 的提交，触发了一次必然失败的 Release 工作流。
5. 后续 PR 使用 squash 合并，本地 `main` 的原始提交与远端 squash 提交分叉，无法通过 `git pull --ff-only` 同步。
6. 本地全量测试启动临时 CC Status 时与正在运行的源码版争用全局 Mutex，配置维护测试超时。
7. GitHub Windows Runner 冷启动较慢，配置维护测试原有的 15 秒 Hook 初始化等待不足，首次 PR CI 超时。
8. Windows PowerShell 模块分析缓存写入仓库目录，造成未跟踪的 `Microsoft/Windows/PowerShell/ModuleAnalysisCache`。

### 根因

- 发布步骤只有说明，没有把“PR 合并完成”设为创建标签的硬前置条件。
- 把多个有依赖关系的原生命令串在一次 PowerShell 调用中，却没有逐步检查 `$LASTEXITCODE`。
- 本地测试实例复用了产品全局 Mutex，测试隔离不足。
- 测试运行器没有显式指定 PowerShell 模块分析缓存位置。
- 异步 WPF 初始化的超时按本机热启动速度设置，没有给 CI 冷启动留出余量。

### 已采取的措施

- 发布修改必须从短期分支通过 PR 合并，禁止直接在本地 `main` 准备发布提交。
- 创建标签前必须确认工作区干净、`HEAD` 等于 `origin/main`、目标标签不存在，并且 PR 必需检查已通过。
- 所有 `git` 和 `gh` 写操作分步执行并检查退出码；前一步失败时不得继续创建或推送标签。
- 配置维护测试使用独立 Mutex，不再要求退出日常运行的源码版。
- Hook 初始化等待上限提高到 30 秒，并在失败时输出进程状态与修复日志。
- 全量测试把 `PSModuleAnalysisCachePath` 指向 `LOCALAPPDATA` 下的绝对缓存路径，避免污染仓库，同时复用 PowerShell 模块分析缓存。
- 安装测试只验证安装与打包职责；应用 UI 和运行契约由独立测试维护。

### 下次发布检查顺序

1. `main` 同步后创建短期发布分支。
2. 更新 `VERSION`、`CHANGELOG.md` 和比较链接。
3. 运行全量测试，确认 `git status --short` 没有测试产物。
4. 提交并推送短期分支，创建 PR。
5. 等待必需 CI 全部通过，再 squash 合并。
6. 重新获取 `origin/main`，确认本地 `HEAD` 与其完全一致。
7. 确认本地、远端均不存在目标标签，再单独创建和推送标签。
8. 等待 Release 工作流生成草稿，检查说明、附件与 SHA-256。
9. 正式发布后再次检查 Release URL、标签提交和本地源码运行状态。
